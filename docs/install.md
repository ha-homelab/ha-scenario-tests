Use the pinned Home Assistant runtime with Python 3.14.2–3.14.x. Install `requirements.lock` with `--require-hashes`, then install this package using `--no-deps .`, as shown in the root README. The lock covers application and test dependencies. A clean environment is required; do not install into your production Home Assistant environment. Use `pip install --no-deps -e .` instead when editing source.

Run `ha-scenario validate examples/stale_sensor.json` first. Validation imports no HA runtime. Then run `ha-scenario run examples/stale_sensor.json --report result.json`. No target server is configured. The only output path comes from your explicit `--report` argument, not the scenario.

For a stronger network boundary:

```sh
docker build -t ha-scenario-tests .
docker run --rm --network none --read-only --tmpfs /tmp:rw,nosuid,size=64m ha-scenario-tests
```

The build needs Internet access for dependencies. The run has no network and a disposable writable `/tmp`; it does not mount the home configuration, Docker socket or credentials. This is an optional deployment recipe; consult the validation record for whether this exact container was executed. Do not add host networking or production mounts.

The subprocess interface strips inherited credentials and `PYTHONPATH`. Worker `-I` uses the installed package. Only PATH, SYSTEMROOT and LANG are inherited; the hash seed is fixed. On Linux the worker library path is derived from the running Python installation's `LIBDIR`, allowing relocatable Python builds to find libpython. An inherited `LD_LIBRARY_PATH` is never copied. The child has a 30 second parent timeout, an inner 20 second timeout, at most 5 seconds of requested timeline waits and 256 captured actions. Native dependency hangs are terminated by the parent timeout.

The pytest plugin is installed automatically. A test can load a scenario with `ha_scenario_tests.schema.load` and call the `scenario_runner` fixture. JUnit is generated by pytest itself. `run_scenario` can also be imported in ordinary Python.
