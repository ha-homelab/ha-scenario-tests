# Протокол проверки

## Проверки разработки 2026-10-15

На macOS arm64 с Python 3.14.7 проверены исходники, строгая схема, блокировка Python I/O, переводы CLI и воспроизводимость SVG. Команда `python -m pytest -q -m 'not runtime'` дала **31 успешный тест**; шесть проверок настоящего HA эта команда явно исключает. `python -m ruff check src tests scripts` прошла. Это не заменяет полный прогон.

Настоящий Home Assistant 2026.10.0 загрузил `automation`, `blueprint`, `trace` и выполнил сценарии таймера присутствия и ручного удержания: ожидаемые вызовы, правильные конечные состояния, ни одной попытки запрещённого I/O. После этого локальный Python завершился с native segmentation fault при очистке интерпретатора. Родительский runner правильно считает такой код завершения ошибкой, даже если до неё получен успешный JSON. **Полный успешный runtime-тест на macOS не заявляется.**

Перед принятием релиза обязателен полный Linux CI: `python -m pytest -q --junitxml=junit.xml`. Отсутствие HA, неправильная версия, тайм-аут и ненулевое завершение процесса считаются ошибкой, а не пропуском теста. Актуальный результат Linux смотрите в CI репозитория. Запуск Docker и проверка физического оборудования в этом протоколе не подтверждены.

## Контролируемые сведения о среде

Worker задаёт `synthetic` в кэше сведений Python о процессоре и отключает `socket.has_ipv6` до импорта HA. Так инициализация платформы не запускает `uname -p`, а urllib3 не выполняет пробное IPv6 bind при импорте. В блокировке I/O нет разрешающих исключений для этих операций. Меняются лишь сведения о среде; триггеры, условия, таймеры, reload, скрипты и отправка сервисных вызовов принадлежат настоящему HA. Эта часть зависит от версии и проверяется закреплённым runtime.

Команды воспроизведения приведены в [английском протоколе](validation.md). SVG показывает синтетические ожидания; он не является измерением производительности или подтверждением состояния реальных реле.
