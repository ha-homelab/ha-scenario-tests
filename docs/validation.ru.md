# Протокол проверки

## Проверка Linux runtime 2026-10-15

[GitHub Actions run 38843681199](https://github.com/ha-homelab/ha-scenario-tests/actions/runs/38843681199) успешно завершился для коммита `0ea7e5a5d24dc89ebe896b1a2387396b3fce18f4`: CPython 3.14.8, Ubuntu и закреплённый Home Assistant 2026.10.0. Полная команда `python3 -m pytest -q` дала **54 passed in 21.42s**, без пропусков. Включены все семь тестов настоящего HA: четыре примера сценариев, намеренно неверные ожидания/запрещённый вызов, JSON-отчёт локализованного CLI и контракт переноса роли. Каждый runtime-тест запускает новый контролируемый worker; намеренно неверные ожидания проверяются именно как ошибки сценария.

В том же запуске прошли Ruff, проверка ссылок/SVG, сборка исходного пакета и wheel, политика публикации исходников и поиск секретов во всей истории. Подтверждено синтетическое выполнение сервисных вызовов и изменение состояний с описанным Python I/O guard. Это не проверка песочницы ОС, запуска Docker или физической работы устройств.

## Проверки разработки на macOS 2026-10-15

На macOS arm64 с Python 3.14.7 проверены исходники, строгая схема, блокировка Python I/O, переводы CLI и воспроизводимость SVG. Команда `python -m pytest -q -m 'not runtime'` дала **47 успешных тестов**; семь проверок настоящего HA эта команда явно исключает. `python -m ruff check src tests scripts` прошла. Это не заменяет полный прогон.

Настоящий Home Assistant 2026.10.0 загрузил `automation`, `blueprint`, `trace` и выполнил сценарии таймера присутствия и ручного удержания: ожидаемые вызовы, правильные конечные состояния, ни одной попытки запрещённого I/O. После этого локальный Python завершился с native segmentation fault при очистке интерпретатора. Родительский runner правильно считает такой код завершения ошибкой, даже если до неё получен успешный JSON. **Полный успешный runtime-тест на macOS не заявляется.**

Перед принятием релиза обязателен полный Linux CI: `python -m pytest -q --junitxml=junit.xml`. Отсутствие HA, неправильная версия, тайм-аут и ненулевое завершение процесса считаются ошибкой, а не пропуском теста. Ссылка выше подтверждает Linux-проверку этой реализации; последующие изменения требуют нового успешного запуска. Запуск Docker и проверка физического оборудования в этом протоколе не подтверждены.

## Контролируемые сведения о среде

Worker задаёт `synthetic` в кэше сведений Python о процессоре и отключает `socket.has_ipv6` до импорта HA. Так инициализация платформы не запускает `uname -p`, а urllib3 не выполняет пробное IPv6 bind при импорте. В Linux ifaddr импортируется под действующим guard через `ctypes.CDLL(None)`: используются символы уже загруженной libc, без запуска `ldconfig`. Обычный поиск библиотек сразу восстанавливается. В блокировке I/O нет разрешающих исключений для этих операций. Меняются лишь сведения о среде; триггеры, условия, таймеры, reload, скрипты и отправка сервисных вызовов принадлежат настоящему HA. Эта часть зависит от версии и проверяется закреплённым runtime.

Команды воспроизведения приведены в [английском протоколе](validation.md). SVG показывает синтетические ожидания; он не является измерением производительности или подтверждением состояния реальных реле.

Runtime-набор также содержит `tests/fixtures/role_transfer.json`: синтетическую проверку, что команда выключает текущую роль, оставляя старую розетку включённой. Это не физическая проверка переноса нагрузки.
